**Paths:**

- `.github/workflows/release.yml:91-96`
- `.github/workflows/taskfleet-release-gate.yml:7-15`

permissions:

permissions:

    contents: read

## P0 — A failed gate can still satisfy `host` and create a GitHub Release

**Paths:**

- `.github/workflows/release.yml:99-105`
- `.github/workflows/release.yml:184-195`
- `.github/workflows/taskfleet-release-gate.yml:25-31`
- `scripts/validate-distribution-topology.sh:81-98`

`build-local-artifacts` depends on the gate, but `host` does not:

```yaml
host:
  needs:
    - plan
    - build-local-artifacts
    - build-global-artifacts
  if: ${{ always()
    && needs.plan.outputs.publishing == 'true'
    && (needs.build-global-artifacts.result == 'skipped'
        || needs.build-global-artifacts.result == 'success')
    && (needs.build-local-artifacts.result == 'skipped'
        || needs.build-local-artifacts.result == 'success') }}
```

When activation is blocked:

1. The gate fails.
2. `build-local-artifacts` is skipped.
3. `build-global-artifacts` is skipped because its dependency was skipped.
4. `host` uses `always()` and explicitly accepts both build jobs being skipped.
5. Therefore its condition is true for a tag push.

The only remaining protection is the gate’s asynchronous API request to cancel the whole workflow. That is not a safe dependency boundary. Cancellation can race job scheduling, be delayed, fail transiently, or stop working after an Actions API behavior change. If `host` starts, it has `contents: write` and executes both:

```sh
dist host ... --steps=upload --steps=release
gh release create ...
```

This is exactly the cargo-dist skipped-dependency behavior the ADR requires the project to close. The current implementation notices the behavior but works around it with cancellation instead of making publication structurally impossible.

**Required fix:**

Make the gate a direct dependency of `host` and require success:

```yaml
host:
  needs:
    - plan
    - custom-taskfleet-release-gate
    - build-local-artifacts
    - build-global-artifacts
  if: >-
    ${{
      always()
      && needs.custom-taskfleet-release-gate.result == 'success'
      && needs.plan.outputs.publishing == 'true'
      && needs.build-global-artifacts.result == 'success'
      && needs.build-local-artifacts.result == 'success'
    }}
```

For this topology, accepting skipped build jobs is unnecessary: the attached plan always has a non-null artifact matrix and release builds require both local and global artifacts. If cargo-dist genuinely needs skipped builds for another supported topology, encode the exact admitted reason rather than accepting every skip.

Also make downstream secret use structurally dependent on a successful gate. `publish-homebrew-formula` is currently transitively protected by successful `host`, which is sufficient only after `host` is fixed.

The validator must inspect the actual host dependency and condition. This assertion is inadequate:

```sh
[[ "$(grep -Fc 'custom-taskfleet-release-gate' .github/workflows/release.yml)" -ge 2 ]]
```

It only counts strings and does not prove that `host` is gated. Add assertions for:

- `host.needs` containing `custom-taskfleet-release-gate`;
- the host condition requiring the gate result to equal `success`;
- no publishing job accepting a failed or skipped gate.

Cancellation can remain defense in depth, but it cannot be the release boundary.

**Candidate CI:** **Release-safety blocker.** Ordinary CI may remain green despite the vulnerability; merge must still be blocked.

### BLOCKER-2: `host` job can run after gate failure because it only observes skipped downstream build jobs

**Paths:**
- `.github/workflows/release.yml`, `host.needs`
- `.github/workflows/release.yml`, `host.if`
- `.github/workflows/release.yml`, `build-local-artifacts.needs`

`host` does not list `custom-taskfleet-release-gate` as a dependency. It depends only on:

```yaml
needs:
  - plan
  - build-local-artifacts
  - build-global-artifacts
```

and accepts skipped build results:

```yaml
if: ${{ always() && needs.plan.outputs.publishing == 'true' &&
  (needs.build-global-artifacts.result == 'skipped' || needs.build-global-artifacts.result == 'success') &&
  (needs.build-local-artifacts.result == 'skipped' || needs.build-local-artifacts.result == 'success') }}
```

When `custom-taskfleet-release-gate` fails, `build-local-artifacts` is skipped because one of its `needs` failed. `build-global-artifacts` is then skipped because one of its own prerequisites is skipped. The `host` job condition accepts both skipped results.

The only remaining protection is the gate job's best-effort API cancellation:

```sh
gh api --method POST "repos/$GITHUB_REPOSITORY/actions/runs/$GITHUB_RUN_ID/cancel"
```

That is a cancellation request, not a scheduling constraint. The current validator only checks that `build-local-artifacts` waits for the gate; it does not check that `host` requires gate success.

Add `custom-taskfleet-release-gate` to `host.needs` and require:

```yaml
needs.custom-taskfleet-release-gate.result == 'success'
```

Similarly, consider gating `plan` itself for tag-push runs to close BLOCKER-1.

**Blocks candidate PR CI?**
No. `needs.plan.outputs.publishing` is false on PRs.
**Blocks R9 merge/acceptance?**
Yes. This is not a hard release-activation boundary.
